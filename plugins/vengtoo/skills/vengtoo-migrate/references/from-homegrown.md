# Migrating from homegrown RBAC

Homegrown authorization has no single file to read. There's usually a role→permission
lookup (a map, a table, an enum) *plus* scattered inline checks in handler/middleware code
— and the inline checks are where the real behavior lives. A permission map saying a role
"has" `customer.update` tells you it can pass a first gate, not that it will actually
succeed; ownership checks, business-rule exceptions, and hardcoded overrides usually live
next to the handler, not in the map.

## Discover

- **Find the permission map** (or table/enum) — this is your starting inventory of
  role → action pairs, but treat it as a first draft, not ground truth.
- **Find every call site** that checks it (`HasPermission(role, action)` or equivalent) —
  read the handler/middleware code around each call, not just the check itself. This is
  where you'll find:
  - Ownership/relationship checks (`resource.OwnerID != user.ID`)
  - Attribute-match checks (`resource.BusinessUnit != user.BusinessUnit`)
  - Hardcoded bypasses (a specific admin email, a "legacy"/"imported" flag that skips
    normal checks, a break-glass account)
  - Business-rule overrides layered on top of the base permission (a fraud-hold block, a
    restricted-export-kind check) — often with a comment explaining *why*, which is useful
    context for whether the rule should even survive the migration
- **Expect inconsistency.** Unlike a declarative policy language, there's no single
  decision point — visually similar endpoints can enforce different rules. Inventory
  **per endpoint**, don't assume uniform behavior across resources that merely look alike.

## Map

| Homegrown pattern | Vengtoo equivalent |
|---|---|
| `RolePermissions[role][action] == true` (flat lookup) | **role** + a type-level **`ALLOW`** policy per resource type/action pair |
| `role == "admin"` / a wildcard `"*"` permission | a dedicated role with **unconditioned** (no `resource_attrs`) policies |
| `resource.OwnerID == user.ID` | **instance-level direct grant** — same limitation as Rego/Cedar/Casbin ownership checks: no dynamic cross-entity condition exists, so this can't be one reusable policy |
| `resource.Field == user.Field` on a **small, fixed** value set (e.g. 2-3 tenants) | one **role per value** + a literal `resource_attrs` condition — same pattern used for tenant scoping elsewhere |
| `resource.Field == user.Field` on an **open-ended/high-cardinality** attribute (e.g. business unit, team, region) | does **not** scale to per-value roles. Needs instance-level grants generated **programmatically** at the point the relationship is established (e.g. when a resource is assigned to someone) — not something to hand-author per pair |
| a hardcoded bypass (specific email, break-glass account) | model as a **dedicated subject** with a broad/admin-equivalent role. Flag this explicitly for the customer to decide whether to carry it forward — this is exactly the kind of debt a migration is a good excuse to clean up, not silently preserve |
| a boolean gate on a resource field (e.g. `FraudHold`, `Escalated`, `LegacyImported`) | a plain **`resource_attrs`** literal condition — these translate cleanly, no workaround needed |
| a relative/computed check (a time delta, a numeric threshold tied to another field) | **doesn't translate** — see below |

## Doesn't translate automatically — flag for human review

- **Ownership/attribute-match checks** — instance-level grants only, per the table above.
  For anything beyond a handful of instances, this needs to be generated by the
  integration at write time, not authored by hand during migration.
- **Relative/computed conditions** (e.g. "more than 24h after this resource's own
  timestamp") — not expressible at all today, not even via the instance-grant workaround.
  Flag it and ask whether the rule is still wanted; if so, it needs to be enforced
  elsewhere (application code) until the platform supports it.
- **Hardcoded exceptions** — don't silently port a break-glass bypass or a legacy-data
  flag into the new model without asking. These often accumulate for reasons that no
  longer apply; migration is the natural point to confirm each one is still intended.
- **Inconsistent enforcement across similar-looking endpoints** — if two endpoints for the
  same resource type enforce different rules, don't average them into one policy. Ask
  which behavior is actually correct; the inconsistency itself may be a bug you're being
  handed the chance to fix, not a spec to preserve exactly.

## Note

There's no "source file" to diff against here — Discover for homegrown auth is closer to
code archaeology than to reading a config. Budget more time for Discover than you would for
a declarative source (Rego/Cedar/Casbin); the translation step itself, once the real rules
are actually understood, tends to be no harder than the others.

Once mapped, hand model creation to `/vengtoo-policies`, then validate with the
`references/shadow.md` method before promoting.
